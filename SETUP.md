# Setup

Instantiate the template by setting a small number of parameters. Everything else, the layer model, the anchor mechanics, the check contracts and the status progression, is invariant and stays untouched.

## Placeholders

Every `{{…}}` marker in the files named under Fill-in order belongs to one of two classes. Class A is instance data that follows from the repository itself. Class B is a project decision that has to be taken before anything is filled. A third group is derived content, produced from the class B decisions rather than substituted for a marker.

### Class A, instance data

| Marker | Definition |
|---|---|
| `{{PROJECT_NAME}}` | The name of this vault instance, used as the title of `HOME.md` and `CLAUDE.md` and in the Promptotyping header of every project knowledge document. |
| `{{REPOSITORY}}` | The repository this instance lives in, as a URL or an `owner/name` slug. |
| `{{DATE}}` | The instantiation date in ISO 8601, written into `created` and `updated` and into the first entry of the settled decisions. |

### Class B, project decisions

| Marker | Definition |
|---|---|
| `{{PURPOSE}}` | One paragraph on what output this vault produces, for whom and under which evidence obligation, whose first sentence names the overall topic of the vault. |
| `{{TOPICS}}` | The controlled topic set, meaning the closed list of topics that assertions may be filed under. Each topic becomes one `MOC-<Topic>.md` in `30_assertions/`. |
| `{{SOURCE_TYPES}}` | The source types this project activates out of `document`, `publication` and `data`. |
| `{{GENRE}}` | The genre of the output, such as strategy, proposal, report or scholarly synthesis. |
| `{{LANGUAGE}}` | The working language of the content, meaning output, assertions and distillates. `knowledge/` and `CLAUDE.md` stay English. |
| `{{VERIFICATION_ROLE}}` | The role and institution holding the authority to establish evidence. |
| `{{REVIEW_MECHANISM}}` | The mechanism fulfilling the machine review contract, meaning the reviewer model and the pairing tooling. The default pairing tooling is `tools/review.py`, whose `emit` and `judge` subcommands let a reviewer from a different model family than the producing agent judge the pairs, which decorrelates error modes. |
| `{{STYLE_SHEET}}` | The rules for the output prose, covering register, citation display and terminology choices. |
| `{{HARNESS_RULES}}` | The harness-specific rules of the exchangeable block at the end of `CLAUDE.md`, such as which commands an agent may run unasked. |

### Derived content

Three things are written rather than substituted. One `MOC-<Topic>.md` per topic of the controlled topic set in `30_assertions/`, schema in `knowledge/schema.md` § Topic map. The topic map link list under "Explore the knowledge" in `HOME.md`, one wikilink per MOC file. The chapter register in `knowledge/state.md`, one row per chapter of the output.

## Fill-in order

1. Take the class B decisions and replace their markers in `knowledge/specification.md`, which records all of them except `{{HARNESS_RULES}}`. That one is written only into the harness block of `CLAUDE.md`, in step 2.
2. Replace the class A markers in `knowledge/index.md`, `schema.md`, `operations.md`, `state.md`, `journal.md`, `specification.md`, `CLAUDE.md` and `HOME.md`. In `CLAUDE.md`, also replace `{{LANGUAGE}}` with the decision from step 1 and `{{HARNESS_RULES}}` with the harness rules, and remove the template note comment at the top.
3. Create one `MOC-<Topic>.md` per topic in `30_assertions/` and write the matching link list into `HOME.md`.
4. Write the chapter register into `knowledge/state.md`. It stays hand-maintained, because a planned chapter follows from no file. The source inventory above it is generated by `python tools/inventory.py . --write` and is left alone here.
5. Remove what belongs to the template alone. Delete `paper/`, the template's own method instance, together with its routing row in the task table of `CLAUDE.md` and the step that validates it in `.github/workflows/checks.yml`. Delete `CHANGELOG.md`, which records template changes and is read in the template repository. Rewrite `README.md`, `CITATION.cff` and `codemeta.json` for the instance, or delete them where the instance is not published. Delete `docs/` if unwanted. Leave `tests/fixtures/` in place, because the test suite runs against it in an instance as well.
6. Run `python tools/validate.py .` and `python -m pytest tests`. A fresh instance prints `W-EMPTY` until the first document enters the production chain, `W-NO-OUTPUT` until the first chapter exists and `W-PLACEHOLDER` while a placeholder is left. Each names work still outstanding and disappears when that work is done. How warnings count toward a run is set out in `knowledge/operations.md` § Check.
7. Commit as the instantiation milestone and note it in `knowledge/journal.md`.

## Conditional folders

Two folders across the chain are used only where the project calls for them. `references/` holds the CSL JSON records of citable-only sources and is needed only when the source type `publication` is active. `glossary/` holds one document per central technical term of the content and is used as the need arises, and an empty glossary is no defect.

## Continuous checking

`.github/workflows/checks.yml` lints the repository with ruff, runs the validator over the template and over `paper/`, and runs the test suite on every push and pull request. An instance removes the `paper/` step together with the folder, and an instance that does not want continuous checking deletes the file.

## Prompt for the first agent session

Start an agent session in the repository root and give it this prompt.

```
Instantiate this Grounded Vault template for my project.

Read SETUP.md, knowledge/index.md and knowledge/schema.md first, then work in
this order and stop for me where the instructions say so.

1. Ask me for the class B decisions from SETUP.md, one question at a time, in
   the order PURPOSE, TOPICS, SOURCE_TYPES, GENRE, LANGUAGE, VERIFICATION_ROLE,
   REVIEW_MECHANISM, STYLE_SHEET, HARNESS_RULES. Propose a concrete default
   where my answer allows one, and do not invent a decision I have not given.
2. Read the class A values off the repository and the current date, and confirm
   them with me in one step.
3. Replace every {{...}} placeholder in the files SETUP.md names under Fill-in
   order with the agreed values and remove the TEMPLATE NOTE comment at the top
   of CLAUDE.md. Do not touch SETUP.md, tests/ or tools/.
4. Create one MOC-<Topic>.md file in 30_assertions/ per topic of the controlled
   topic set, following the topic map schema, and replace the topic map line in
   HOME.md with one wikilink per MOC file.
5. Write the chapter register into knowledge/state.md, one row per chapter of
   the output, all rows at writing status planned.
6. Remove the template-only files as step 5 of SETUP.md under Fill-in order
   says. Ask me before rewriting or deleting README.md, CITATION.cff and
   codemeta.json.
7. Run `python tools/validate.py .`. Fix every error, and act on every warning
   as knowledge/operations.md § Check says. A fresh instance keeps W-EMPTY,
   W-NO-OUTPUT and W-PLACEHOLDER until content and placeholder replacement have
   removed their cause, and any other warning is fixed now.
8. Commit the instantiation as one milestone and append a dated entry to
   knowledge/journal.md naming the decisions taken.

Report what you filled, which MOC files you created and the final validator
output.
```

## Installing the dependencies

The validator needs PyYAML, the test suite additionally pytest. With uv, `uv sync` installs both from `pyproject.toml`. Without uv, `pip install pyyaml pytest` covers the same set.

## First production cycle

The smallest full pass carries one source from the ground to a written paragraph and exercises every layer and every rule before scale does. It is run in full before a second source is touched, for the reason given in `knowledge/operations.md` § Production order. The procedures belong to `knowledge/operations.md` and the document skeletons to `knowledge/schema.md`.

1. Acquire one source, per `operations.md` § Acquire.
2. Ingest it into its Markdown representation, per § Ingest. A publication has no representation and goes straight to the next step.
3. Distill it, per § Distill, including the quotation check for a publication while the full text is at hand.
4. Build one assertion from the distillate and register it in its topic map, per § Build assertions.
5. Write one chapter of a single paragraph with one `Grounded in` footnote and, where the synthesis calls for one, one posit footnote, per § Write chapters.
6. Check after each step with `python tools/validate.py .`, per § Check. The first ingested representation clears `W-EMPTY` and the first chapter clears `W-NO-OUTPUT`, so the list of warnings shortens as the cycle proceeds. Once the chapter stands, `python tools/validate.py . --chapter 40_output/<slug>` judges it for acceptance.
