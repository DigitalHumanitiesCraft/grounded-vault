# Distillate: Obsidian Developer Documentation, MetadataCache

The API reference of the MetadataCache class states how Obsidian decomposes an internal link into path and subpath and what the two link registers of the cache, resolved and unresolved links, actually map onto.

## Core statements

- A linktext is any internal link composed of a path and a subpath, the linkpath is the path part of a linktext, and the subpath is the heading or block ID part of it. ^s1
  > "Linktext is any internal link that is composed of a path and a subpath, such as 'My note\#Heading' Linkpath (or path) is the path part of a linktext Subpath is the heading/block ID part of a linktext." (obsidiandocsmetadatacache, MetadataCache, § MetadataCache class)
- The property `resolvedLinks` contains all resolved links and maps the path of each source file to an object of destination file paths with the link count. ^s2
  > "Contains all resolved links. This object maps each source file's path to an object of destination file paths with the link count." (obsidiandocsmetadatacache, MetadataCache, § Properties, row resolvedLinks)
- The property `unresolvedLinks` contains all unresolved links and maps each source file to an object of unknown destinations with count. ^s3
  > "Contains all unresolved links. This object maps each source file to an object of unknown destinations with count." (obsidiandocsmetadatacache, MetadataCache, § Properties, row unresolvedLinks)
- Both link registers carry the type `Record<string, Record<string, number>>`, a mapping of string to a mapping of string to number. ^s4
  > "<code>Record</code><code>&lt;string, </code><code>Record</code><code>&lt;string, number&gt;&gt;</code>" (obsidiandocsmetadatacache, MetadataCache, § Properties, type column of resolvedLinks and unresolvedLinks)
- The source paths of the unresolved link register are vault absolute paths, as in the resolved link register. ^s5
  > "Source paths are all vault absolute paths, similar to <code>resolvedLinks</code>." (obsidiandocsmetadatacache, MetadataCache, § Properties, row unresolvedLinks)
- The method `fileToLinktext` generates a linktext for a file, using the file name where it is unique and the full path where it is not. ^s6
  > "<p>Generates a linktext for a file.</p><p>If file name is unique, use the filename. If not unique, use full path.</p>" (obsidiandocsmetadatacache, MetadataCache, § Methods, row fileToLinktext; the cell markup is reproduced, because the two sentences stand in separate paragraph elements and no unmarked concatenation of them occurs in the source)
- The method `getFirstLinkpathDest` returns the best match for a linkpath. ^s7
  > "Get the best match for a linkpath." (obsidiandocsmetadatacache, MetadataCache, § Methods, row getFirstLinkpathDest)
- The event `changed` is called when a file has been indexed and its updated cache is now available. ^s8
  > "Called when a file has been indexed, and its (updated) cache is now available." (obsidiandocsmetadatacache, MetadataCache, § Methods, row on('changed'))
- The event `changed` is not called when a file is renamed, for performance reasons, and a caller must hook the vault rename event for that case. ^s12
  > "Note: This is not called when a file is renamed for performance reasons. You must hook the vault rename event for those." (obsidiandocsmetadatacache, MetadataCache, § Methods, row on('changed'))
- The resolution of a file for the two link registers happens sometimes after that file has been indexed. ^s9
  > "Called when a file has been resolved for <code>resolvedLinks</code> and <code>unresolvedLinks</code>. This happens sometimes after a file has been indexed." (obsidiandocsmetadatacache, MetadataCache, § Methods, row on('resolve'))
- The event `resolved` fires when all files have been resolved, and it fires again each time files are modified after the initial load. ^s10
  > "Called when all files has been resolved. This will be fired each time files get modified after the initial load." (obsidiandocsmetadatacache, MetadataCache, § Methods, row on('resolved'))
- The file is generated automatically by API Documenter and is not to be edited. ^s11
  > "Do not edit this file. It is automatically generated by API Documenter." (obsidiandocsmetadatacache, MetadataCache, § lead comment)

## Terms

- **linktext**: an internal link composed of a path and a subpath
  > "Linktext is any internal link that is composed of a path and a subpath" (obsidiandocsmetadatacache, MetadataCache, § MetadataCache class)
- **subpath**: the heading or block ID part of a linktext
  > "Subpath is the heading/block ID part of a linktext." (obsidiandocsmetadatacache, MetadataCache, § MetadataCache class)

## Open questions

- The reference describes the two link registers as mappings onto destination file paths and unknown destinations respectively, and does not say how the subpath of a linktext is treated when the registers are built, so whether a link whose file resolves but whose block does not counts as resolved is not stated here.
- The reference gives no schema for the objects returned by `getCache` and `getFileCache`, so what the cache holds per file beyond the link registers cannot be read off this page.
- The reference states that `resolve` fires sometimes after a file has been indexed, without saying what determines that delay or how a caller knows the registers are current.

## Appraisal

The page is generated API reference of the vendor, which makes it the authoritative statement of the interface and at the same time a thin one, since generated documentation carries the prose the source comments happened to hold. Its value for this vault is the type of the two link registers, which fixes what the application will and will not report about a broken link. Its limit is that an interface description is not a behaviour specification, so the page settles what shape the data has and leaves the resolution semantics behind that shape unstated.
